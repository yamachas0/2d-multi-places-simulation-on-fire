# LLM エージェントの圧縮記憶設計 メモ

シンプルな rolling-buffer memory の限界と、長期記憶を保つための「圧縮 × 短期 raw」ハイブリッド設計。

---

## 1. 出発点の問題

LLM ベースのエージェントが N 步 (例: 100 step) のシミュレーションを走るとき、各 step で:

1. その step での思考 (memory + reasoning) を生成
2. agent の memory リスト (内部の dict 列) に append
3. 次 step の prompt に「直近 N 件」だけを乗せる (= rolling buffer)

これだと:
- 長い run の途中で **古い memory が prompt から消える**
- 「3 step 前にコクヨを訪問した」「7 step 前に X さんと話した」を agent が **忘れる**
- 結果: 同じ場所を再訪、同じ人に同じことを言う、進展しない、を繰り返す

**rolling buffer サイズを増やせば直る** (例 5→15) が:
- 毎 step uncached input が大幅に増えてコストが ~30% 増
- それでも「100 step 前」 は依然として消える

---

## 2. 人間の脳との類比

人間の脳は全部の出来事を生で覚えてない。**短期記憶 (海馬) → 長期記憶 (大脳皮質、抽象化)** に圧縮しながら保持する。
- 直近 (数分): 詳細・色・声・ニュアンス込みの **生々しい記憶**
- 長期 (数日以上): エピソードの**要約**、「あの店に行って X さんと話した」レベルに抽象化

LLM もこの構造を真似できる。LLM の特性 (要約・抽象化が得意) を活かす好機。

---

## 3. 提案: sliding window archive + 直近 raw のハイブリッド

```
agent.archived_summaries = []   # 要約 (固定保管、step が進んでも消えない)
agent.memory             = []   # 直近 raw、常に N 件まで rolling
```

### 動作

各 step:
1. LLM が memory + reasoning を生成 → `agent.memory.append(new)`
2. `len(agent.memory) > N` なら `pop(0)` (最古を捨てる)
3. **step が N の倍数になった瞬間**、直近 N 件 (= agent.memory 全件) を 1 文に要約させて `agent.archived_summaries.append(summary)`
   - 要約は LLM (例: Gemini) で生成。短い prompt + 簡素な system_prompt で OK
   - raw は捨てない (raw window はそのまま rolling 続行)

prompt 構築時:
- `archived_summaries` (全件、固定) + `agent.memory` (直近 raw N件) を memory section として LLM に渡す

### step 経過 (N=10, K=N=10 の例)

| step | archived (要約) | raw (直近10件) | 合計 prompt 件数 |
|---|---|---|---|
| 5 | 0 | 5 | 5 |
| 10 | 1 (step1-10) | 10 (step1-10) | 11 (raw とarchive 重複瞬間) |
| 11 | 1 | 10 (step2-11) | 11 |
| 15 | 1 | 10 (step6-15) | 11 |
| **16** | **1** | **10 (step7-16)** | **11** ← step11-15 は raw に残ってる ✅ |
| 20 | 2 (1-10, 11-20) | 10 (step11-20) | 12 |
| 21 | 2 | 10 (step12-21) | 12 |
| 100 | 10 | 10 (step91-100) | 20 |

**ポイント**:
- raw window が「過去 N step分」を保持してる間に要約 archive が走るので、**ギャップなし** (= memory が消える瞬間がない)
- 要約と raw が一時的に重なる瞬間 (step N, 2N, 3N, ...) があるが、トークンの二重消費は微々たるもの

---

## 4. パラメータ N の選び方

「N 何 step ごとに archive するか + raw を何件保持するか」がコストと質を決める。

### 試算 (本番想定: 100 step / 22 agent, モデル gemini-2.5-flash-lite)

| N | archive件 | raw件 | prompt token/call | 要約 call/人 | 追加コスト/run |
|---|---|---|---|---|---|
| **N=5**  | 20 | 5  | 1200 | 20 | **¥65** |
| **N=10** | 10 | 10 | 1500 | 10 | ¥78 |
| **N=20** | 5  | 20 | 2200 | 5  | ¥122 |

### 観察

1. **N が小さいほど安い** ─ 「短い要約 × 多数」のほうが「長い要約 × 少数 + raw 多」より token 効率が良い (raw 1件 ≒ 80t vs 要約 1件 ≒ 40-120t、N が大きいほど 1要約が膨らむ)
2. **N=5 は長期記憶の粒度が最高** ─ 20 個の独立したエピソードが残る (「コクヨ訪問」「X と話した」「Y で気づいた」を独立保存)
3. **N=20 は短期文脈が強い** ─ raw 20件 = 直近40分の生記憶、turn-taking や直近の対話継続には有利

### コスト効果 (質/コスト)

> **N=5 が最もコスト効果高い** ─ コスト最安、長期記憶の粒度も最高、要約品質も担保される

ただし以下の場合は別:
- 直近の文脈強度を最重視するシナリオ → N=20 がよい
- バランス型 → N=10

## 5. 実装の勘所

### 要約 system_prompt の例

```
あなたは agent の長期記憶を生成します。
以下は、ある人物が直近 N step (実時間 ~10 分) の間に書いた memory + reasoning です。
これを **1 文 (60-120字) のエピソード要約** にまとめてください。

ルール:
- 「いつ・どこで・誰と・何が起きた・どう感じた」を圧縮
- 数字や具体的な発言は本人が後で参照したくなるレベルで保持
- 「色んなことがあった」のような抽象語は禁止
- 出力は要約文 1 文のみ。前置き・コードブロック禁止
```

### archive の表示形式

prompt 内では明示的に区別する:

```
PREVIOUS MEMORY:
[要約 step1-10] 港南口広場で X さんと未来像を話した。新幹線改札を通ってアトレ品川へ移動、A商店街の構造に気づいた。
[要約 step11-20] 第一京浜を渡って高輪側へ。品川神社で Z と街の歴史議論。御殿山公園で休憩。
[step21] (生記憶) コクヨに到着、受付の Y 担当者と話を始める。
[step22] (生記憶) Y 担当者から「学校の机以外で集中できる場所」について聞く。
[step23] (生記憶) ...
```

### コスト最適化の追加余地

- **要約 LLM call は cache に乗せやすい**: agent persona が固定なので、要約 prompt の system_prompt 部分は cache 共通
- **要約タイミングを並列化**: simulation の step 内 LLM call と同時に async で要約走らせれば、wall-time 増えない

## 6. 別案との比較

| 案 | 仕組み | 利点 | 欠点 |
|---|---|---|---|
| (a) memory_size を増やす (5→10/15) | rolling 件数を増やすだけ | 実装容易、追加 LLM call なし | 長期は依然消える、token 線形増 |
| (b) 圧縮ハイブリッド (本案) | rolling raw + 段階的要約 archive | 長期保持、token 効率良 | 要約 call 追加、設計やや複雑 |
| (c) 重要度ベース選別 | marker 検出した重要 memory だけ rolling 外で保持 | 既存の rule-based 訪問履歴と同じ思想 | 「何が重要か」の定義が難しい |
| (d) embedding 検索 (RAG的) | memory を embedding 化、prompt 構築時に関連性高いものだけ取り出す | 長期 + 関連性高い記憶だけ表示 | 実装重い、embedding model 必要、call 重 |

(b) は (a)(c) より洗練、(d) より軽量、というスイートスポット。

## 7. 議論したい論点

- **要約のサイクル N=5 / 10 / 20** どれが最適か (本資料は N=5 推し)
- **要約 prompt の品質** ─ どこまで具体性を保たせるか、抽象化しすぎないか
- **archive の上限** ─ 100 step 以上の長 run なら archive も増え続ける。月単位の run なら archive にもまた一段の圧縮層 (二段階圧縮) が要るか
- **archive と raw の境界の扱い** ─ 要約と raw の重複瞬間で LLM が混乱しないか、明示的なラベル付けで吸収できるか
- **embedding 検索 (RAG) との併用** ─ archive 数十件以上になったら、関連性で取り出す方が token 効率良いか
